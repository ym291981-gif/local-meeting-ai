## セッション1: Phase 1 MVP初期実装(要件定義書→動くコード)(2026-08-09〜10)

### 背景

`docs/requirements.md` の要件定義書をもとに、Phase 1 MVP(Web UI、リアルタイム
音声取得・文字起こし・話者分離・議事録生成)の実装プランを作成し、そのプラン
に沿ってバックエンド(FastAPI)・フロントエンド(HTML/CSS/JS)・スクリプト
群をゼロから一気通貫で実装したセッション。このセッションの最後の時点では
`HF_TOKEN`が未設定で、話者分離だけ未検証のまま終わっている(→次の
「セッション2」で解消)。

### つまずいた点・苦戦した点

1. **開発環境そのものが何も入っていなかった**
   - `python`コマンドも`ollama`コマンドも見つからず、最初のコマンド実行から
     失敗した。`winget`でPython 3.11とOllamaを個別にインストールし、PATHが
     反映されるようシェルを再起動する、という地道な準備が必要だった。

2. **ライブラリ同士のバージョン競合**(`httpx`)
   - `requirements.txt`に固定した`httpx==0.28.1`が、後から追加した`ollama`
     パッケージの要求バージョン(`<0.28.0`)と衝突し、インストールが失敗した。
     `httpx==0.27.2`に下げることで解消。

3. **FastAPIの`204 No Content`ルートで謎のアサーションエラー**
   - 参加者削除APIに`status_code=204`と`-> None`の返り値注釈を両方つけた
     ところ、FastAPIの起動時に`assert is_body_allowed_for_status_code`
     で失敗する現象が発生。「204はボディを持てない」という仕様と、FastAPI
     内部のレスポンスモデル推論の相性が悪かった。`response_model=None`を
     明示することで解決したが、エラーメッセージからは原因が読み取りにくく
     調査に時間がかかった。

4. **PowerShellでの文字コード破壊(モジバケ)**
   - `AudioChunker`(`backend/app/audio/chunker.py`)内の日本語コメントが、
     文字列置換系のコマンドを経由した際にASCIIの`?`だけの文字列に化けて
     ファイルが壊れる現象が発生。ユーザー自身がエディタで気づいて報告して
     くれたことで発覚した。原因を厳密に特定するより、該当ファイルを
     いったん英語コメントで書き直し、Pythonでバイト列を確認して「壊れて
     いないこと」を確認する方針に切り替えた。

5. **テストで発覚した`AudioChunker`のロジックバグ**
   - チャンク分割ロジックが`min_chunk_seconds`という内部変数に依存しており、
     テスト用の短い`chunk_seconds`を渡すと境界判定がずれてチャンクが
     正しく切り出されない不具合があった。設計を「先読みウィンドウ
     (`_lookahead_samples`)でチャンク境界の無音を探す」方式に整理し直す
     ことで解消。単体テストを先に書いていたおかげで気づけた。

6. **Ollamaのモデルタグ名が想定と違った**
   - `.env.example`に書いた`qwen3:4b-instruct-2507`という名前で
     `ollama pull`したところ、「manifest not found」エラーで失敗。
     Web検索でOllama公式のタグ一覧を確認し、正しいタグ
     `qwen3:4b-instruct-2507-q4_K_M`に修正した。ドキュメント上の記憶
     だけでモデル名を決めてしまうと、実際のレジストリと食い違うことがある
     という教訓。

7. **テストでのSQLAlchemy `DetachedInstanceError`**
   - `test_api_smoke.py`内で、DBセッションを閉じた後に`speaker.id`や
     `utterance.id`にアクセスしたところ、オブジェクトが「detached」状態
     になっていてエラーになった。セッションを閉じる前にIDをローカル変数
     へ退避することで解決。ORMオブジェクトの生存期間(セッションのスコープ)
     を意識する必要があった。

8. **PowerShellでのGitコミットメッセージ記法**
   - Bash向けの`git commit -m "$(cat <<'EOF' ... EOF)"`という複数行メッセージ
     の書き方をそのままPowerShellで実行してしまい、構文エラーになった。
     コミットメッセージを一時ファイルに書き出し、`git commit -F <file>`で
     読み込む方式に変更して回避した。シェルの違い(Bash想定のコマンドは
     PowerShellでは動かない)を意識する必要があった。

9. **GitHubリポジトリ連携の進め方が最初分からなかった**
   - ユーザーはGit自体は使い慣れていたが、「ローカルで作った変更を初めて
     GitHubに上げる」という手順(空リポジトリの作成→リモートURLの登録→
     push)に馴染みがなかった。また作業中にGitHubのページが開けなくなる
     トラブルもあった。`gh`コマンドが未導入だったため、ユーザーに
     GitHub上で空リポジトリを作成してもらい、そのURLを`git remote add`
     する手順を案内する形で対応した。

10. **スクリプトをリポジトリのルートから実行すると`ModuleNotFoundError`**
    - `python scripts/xxx.py`のように素の`python`コマンドで実行すると、
      仮想環境(`.venv`)にインストールした`numpy`等が見つからずエラーに
      なった。`.venv\Scripts\python.exe`を明示的に指定して実行する必要
      があった。

### 工夫した点・対応方法

1. **コードを書くだけで終わらせず、実機(実際のGPU・マイク・Ollama)で
   段階的に検証した**
   - 音声デバイス一覧の取得→内部音声の録音→Whisperでの単体文字起こし
     →Ollama連携→フルE2Eデモ、という順で1機能ずつ実際に動かして確認した。
     これにより、コードレビューだけでは見つからなかった不具合
     (チャンク分割ロジック、モデルタグ名の誤りなど)を早期に発見できた。

2. **AI/ハードウェア依存部分をテストから切り離す設計**
   - 実際のGPUやマイク、Ollamaが無くてもAPI・DBロジックを検証できるよう、
     `FakeOrchestrator`という差し替え可能なテストダブルを用意し、FastAPIの
     依存性注入(DI)の仕組みでテスト時だけ本物のオーケストレーターと
     入れ替えられるようにした。これにより自動テストがCI環境でも軽量に
     動く状態を維持できた。

3. **障害が起きても議事録生成システム全体を止めない、段階的なフォール
   バック設計**
   - 個々のAI処理(文字起こし・話者分離)が失敗しても、そのチャンクだけ
     スキップしてパイプライン全体は継続する設計にした。さらにメインループ
     自体が致命的エラーで落ちた場合でも、会議のステータスを確実に
     `finalize`する保護コードを入れ、データが不整合な状態で残らないように
     した。

4. **手動編集を上書きしない、というデータ整合性の設計**
   - 議事録生成のたびにDBから最新のスナップショットを読み直し、そこに
     差分を当てる方式にすることで、ユーザーがUI上で手動編集した内容が
     AIの次回生成で勝手に消えてしまわないようにした。

5. **TTS(`pyttsx3`)で合成した固定デモ音声を使い、E2Eテストを再現可能に
   した**
   - 実際の会議を録音しなくても、毎回同じ内容の音声を生成して通しの動作
     確認ができるように`generate_demo_audio.py`と`run_demo_e2e.py`を用意
     した。これにより「毎回同じ入力で結果を比較できる」再現性のある
     検証環境を作れた。

6. **文字コード破壊など「原因が分からない異常」に遭遇した際は、まず
   影響範囲を確認してから最小限の修正に留める**
   - `chunker.py`が壊れた際、他のファイルへの影響有無をまず確認し、
     被害が1ファイルに留まっていることを確かめた上で、そのファイルだけ
     クリーンな内容で書き直す(かつPythonでバイト列を検証する)という
     地に足の着いた対応を取った。

### 今後の課題(このセッション終了時点での引き継ぎ事項)

- `HF_TOKEN`が未設定のため、話者分離(pyannote)は実機で未検証のまま
  セッションを終えた(→この課題は「セッション2」で解消された)。
- 話者クラスタリングの精度そのものは未検証。

## セッション2: HF_TOKENの手動セットアップと話者分離の動作確認(2026-08-10)

### 背景

前回までの開発(「セッション1」)で「`HF_TOKEN`(Hugging Faceのアクセス
トークン)が未設定のため、話者分離(pyannote)は検証できていない」という
状態で引き継いだ。今回はこの手動セットアップを行い、実際に話者分離まで
含めて動作確認することが目的だった。

### つまずいた点・苦戦した点

1. **Hugging Faceの「利用規約同意」の仕組みが分かりにくかった**
   - pyannoteの学習済みモデルは「gated(門番付き)モデル」と呼ばれ、モデルの
     ダウンロード前にWebページ上で利用規約に同意する必要がある。しかも
     関連する複数のモデル(`speaker-diarization-3.1`, `segmentation-3.0`,
     `embedding`)それぞれで個別に同意が必要だった。
   - 同意フォームの「Company/university」「Website」といった入力欄の意味が
     分かりにくかった(個人利用でも適当な値で通ることを確認した)。

2. **`.env`と`.env.example`の違い、保存・反映のタイミングが分かりにくかった**
   - どちらのファイルを編集すべきか混乱しやすい。
   - ファイルを保存しても、サーバーを再起動しないと環境変数が反映されない。

3. **表面的なエラーメッセージだけでは原因が分からない、根深い依存関係の
   バージョン不整合が複数重なっていた**(ここが最も苦戦した部分)
   - `Pipeline.from_pretrained() got an unexpected keyword argument 'token'`
     → コードが渡す引数名(`token`)と、インストール済み`pyannote.audio==3.3.2`
     が期待する引数名(`use_auth_token`)が異なっていた。
   - 引数名を直しても `hf_hub_download() got an unexpected keyword argument
     'use_auth_token'` → 今度は`huggingface_hub`側が1.0以降で`use_auth_token`
     を完全に廃止しており、古い`pyannote.audio`と噛み合わなくなっていた。
   - さらに `SpeakerDiarization.__init__() got an unexpected keyword argument
     'plda'` → そもそも使っていたモデル`pyannote/speaker-diarization-
     community-1`自体が、最新の`pyannote.audio 4.0`系専用に作られたもので、
     プロジェクトが(VRAM急増バグ回避のため意図的に)固定している`3.3.2`系
     とは根本的に非互換だった。
   - 1つのエラーを直すと次のエラーが出る、という「エラーの層」を1枚ずつ
     剥がしていく必要があり、原因特定に一番時間がかかった。

4. **Windows特有のライブラリの不具合**
   - `speechbrain`(pyannoteの話者embeddingモデルが内部で使うライブラリ)に、
     Windowsのパス区切り(`\`)を想定していない判定処理があり、不要な`k2`
     モジュールを要求して`ImportError`で落ちる、という一見関係ない場所で
     クラッシュする不具合があった。
   - これは`speechbrain`本体の既知バグ(修正PRはあるが未リリース)で、
     こちらのコードの問題ではなかった分、原因特定に時間がかかった。

5. **Pythonの例外にならない、プロセスそのもののクラッシュ**
   - Whisper(ctranslate2)と話者分離(torch)を両方GPUで動かした際、
     `Could not load symbol cudnnGetLibConfig. Error code 127` という
     メッセージの直後にプロセスが無言で終了する現象が発生。
   - 通常のPythonの`try/except`では捕まえられない、ネイティブライブラリ
     (cuDNN)のバージョン競合が原因で、ログのtracebackが出ないため
     「何が起きたか」を推測するのに苦労した。

6. **LLM(Qwen3)の出力ゆらぎによる想定外のバグ**
   - 議事録生成AIが、本来「辞書のリスト」で返すべき項目
     (`changes_from_previous`)を「文字列のリスト」で返してしまい、
     画面表示時に500エラーになった。検証処理が「リストかどうか」しか
     チェックしておらず、「リストの中身の型」まで見ていなかったのが原因。

7. **コミット直前にAPIトークンの誤混入を発見**
   - `.env`(本物のトークンが入る、Git管理対象外のファイル)を編集する過程で、
     誤って`.env.example`(Gitで管理される、サンプル用のファイル)側にも
     実際のトークンの値が書き込まれてしまっていた。
   - `git diff`でコミット前に差分を必ず確認する習慣のおかげで、公開前に
     気づいて修正できた。

### 工夫した点・対応方法

1. **エラーを1つずつ、実際にコマンドで再現・検証してから直す**
   - チャットのログを読むだけで判断せず、実際にPythonスクリプトで
     「そのステップだけ」を単独実行して、エラーが再現するか・修正で
     直るかをその都度確認しながら進めた(推測で直して終わり、にしない)。

2. **VRAM対策のために元々あった「3.3.2固定」という制約を守ったまま、
   モデル選定を修正**
   - 最新モデル(`community-1`)を使うのをやめて、`3.3.2`と互換性のある
     一世代前のモデル(`speaker-diarization-3.1`)に切り替えることで、
     既存のVRAM対策の方針を崩さずに問題を解決した。

3. **サードパーティライブラリの既知バグを、ライブラリ自体を書き換えずに
   実行時パッチ(モンキーパッチ)で回避**
   - `speechbrain`の不具合は、Windows専用の直接的な原因(Unix限定のパス
     判定)が特定できたため、起動時に該当処理だけを差し替えるコードを
     自作して対応した。将来ライブラリ側が修正されても実害がない書き方
     (例外時は元の挙動にフォールバック)にしている。

4. **GPU競合は「両方GPU」を諦め、負荷の低い方をCPUに逃がす設計に変更**
   - cuDNNのバージョン競合はライブラリ間の根本的な問題で、その場では
     修正できない。文字起こし(Whisper)をGPUに残し、話者分離をCPUに
     回すことで、機能を落とさずに安定性を確保した(README にも
     理由を明記し、あとで見返せるようにした)。

5. **LLM出力の型チェックを「型」だけでなく「中身の型」まで厳格化**
   - 既存の「前回議事録を上書きしない」という設計方針(README記載)に
     合わせて、不正な形式が来た場合は素直に「失敗」として前回の議事録を
     保持する、という一貫した挙動になるように検証処理を強化した。

6. **コミット前に必ず`git status` / `git diff`で内容を目視確認する**
   - 今回、実際にAPIトークンの誤混入を防げたのはこの手順のおかげ。
     「変更した意図」と「実際の差分」が一致しているかを毎回確認する
     ことの重要性を再認識した。

### 今後の課題(未解決)

- **話者クラスタリングの精度**: 実際に試した際、短い会話(1分程度)で
  `speaker_01`〜`speaker_10`以上に分裂してしまう問題が残っている。
  `SPEAKER_SIMILARITY_THRESHOLD`(現在0.45)の調整、または
  `pyannote/embedding`(比較的古いモデル)自体の精度限界の可能性がある。
  次回以降のセッションで取り組む予定。
  → この課題は「セッション3」で対応した。

## セッション3: 話者クラスタリング精度の改善(2026-08-24)

### 背景

セッション2の未解決課題だった「短い会話で話者が `speaker_01`〜`speaker_10` 以上に
分裂する」問題に取り組んだ。しきい値だけの問題ではなく、割り当て方そのものに
過分裂を招く実装があった。

### つまずいた点・苦戦した点

1. **症状は「しきい値が厳しい」に見えたが、原因は複数重なっていた**
   - 既定のコサイン距離しきい値 `0.45` は、pyannote 3.1 本体のクラスタしきい値
     (約 `0.70`) よりかなり厳しく、同一人物でも新規IDになりやすかった。
   - それ以上に効いていたのが、(a) 0.3秒程度の短い区間ごとに古い
     `pyannote/embedding` でベクトルを取り直していたこと、(b) Whisperの
     セグメントごとに `assign()` を呼んでいたこと。同じチャンクの同じ話者でも
     短いクリップのノイズで別IDになっていた。

2. **話者分離パイプラインは、すでに良い embedding を持っていた**
   - `speaker-diarization-3.1` は内部で WeSpeaker
     (`pyannote/wespeaker-voxceleb-resnet34-LM`) を使っている。
   - それなのに横断クラスタリングだけ古い `pyannote/embedding` を別ロードしており、
     モデルの世代も尺度も揃っていなかった。
   - パイプラインは `return_embeddings=True` で「ローカル話者ごとの代表ベクトル」
     を返せる。短いクリップを切って再計算する必要はなかった。

### 工夫した点・対応方法

1. **短いクリップごとではなく、チャンク内のローカル話者ごとに1つの embedding を使う**
   - `return_embeddings=True` の代表ベクトルを、そのローカルラベルの全区間で共有する。
2. **チャンク内の同じローカルラベルは `assign()` を1回だけにする**
   - Whisperセグメントの数だけクラスタリングしていたのをやめ、過分裂を止めた。
3. **L2正規化してから距離計算・重心更新する**
   - ベクトルの長さの違いで距離が歪まないようにした。話者統合時も正規化する。
4. **既定しきい値を `0.45` から `0.65` へ変更**
   - オンライン(貪欲)割当なので、バッチクラスタの `0.70` より少し厳しめに残した。
   - `.env` の `SPEAKER_SIMILARITY_THRESHOLD` で調整できる。
5. **診断用スクリプト `scripts/inspect_speaker_clustering.py` を追加**
   - 実音声でチャンクごとのローカル/グローバル話者数と距離を見られるようにした。

### 今後の課題

- 実会議音声での最終確認は、このセッションでは自動テスト(ロジック)まで。
  実マイク/Zoomでの過分裂が残る場合は、診断スクリプトの距離分布を見て
  しきい値を微調整する。
- 声がとても似ている別人をまとめすぎる場合は、しきい値を少し下げる
  (例: `0.55`)。
