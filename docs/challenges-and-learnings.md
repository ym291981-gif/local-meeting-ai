## セッション1: Phase 1 MVP初期実装(要件定義書→動くコード)(2026-08-09〜10)

### 背景

`docs/requirements.md` の要件定義書をもとに、Phase 1 MVP(Web UI、リアルタイム
音声取得・文字起こし・話者分離・議事録生成)の実装プランを作成し、そのプラン
に沿ってバックエンド(FastAPI)・フロントエンド(HTML/CSS/JS)・スクリプト
群をゼロから一気通貫で実装したセッション。このセッションの最後の時点では
`HF_TOKEN`が未設定で、話者分離だけ未検証のまま終わっている(→次の
「セッション2」で解消)。

### つまずいた点・苦戦した点

1. **開発環境そのものが何も入っていなかった**
   - `python`コマンドも`ollama`コマンドも見つからず、最初のコマンド実行から
     失敗した。`winget`でPython 3.11とOllamaを個別にインストールし、PATHが
     反映されるようシェルを再起動する、という地道な準備が必要だった。

2. **ライブラリ同士のバージョン競合**(`httpx`)
   - `requirements.txt`に固定した`httpx==0.28.1`が、後から追加した`ollama`
     パッケージの要求バージョン(`<0.28.0`)と衝突し、インストールが失敗した。
     `httpx==0.27.2`に下げることで解消。

3. **FastAPIの`204 No Content`ルートで謎のアサーションエラー**
   - 参加者削除APIに`status_code=204`と`-> None`の返り値注釈を両方つけた
     ところ、FastAPIの起動時に`assert is_body_allowed_for_status_code`
     で失敗する現象が発生。「204はボディを持てない」という仕様と、FastAPI
     内部のレスポンスモデル推論の相性が悪かった。`response_model=None`を
     明示することで解決したが、エラーメッセージからは原因が読み取りにくく
     調査に時間がかかった。

4. **PowerShellでの文字コード破壊(モジバケ)**
   - `AudioChunker`(`backend/app/audio/chunker.py`)内の日本語コメントが、
     文字列置換系のコマンドを経由した際にASCIIの`?`だけの文字列に化けて
     ファイルが壊れる現象が発生。ユーザー自身がエディタで気づいて報告して
     くれたことで発覚した。原因を厳密に特定するより、該当ファイルを
     いったん英語コメントで書き直し、Pythonでバイト列を確認して「壊れて
     いないこと」を確認する方針に切り替えた。

5. **テストで発覚した`AudioChunker`のロジックバグ**
   - チャンク分割ロジックが`min_chunk_seconds`という内部変数に依存しており、
     テスト用の短い`chunk_seconds`を渡すと境界判定がずれてチャンクが
     正しく切り出されない不具合があった。設計を「先読みウィンドウ
     (`_lookahead_samples`)でチャンク境界の無音を探す」方式に整理し直す
     ことで解消。単体テストを先に書いていたおかげで気づけた。

6. **Ollamaのモデルタグ名が想定と違った**
   - `.env.example`に書いた`qwen3:4b-instruct-2507`という名前で
     `ollama pull`したところ、「manifest not found」エラーで失敗。
     Web検索でOllama公式のタグ一覧を確認し、正しいタグ
     `qwen3:4b-instruct-2507-q4_K_M`に修正した。ドキュメント上の記憶
     だけでモデル名を決めてしまうと、実際のレジストリと食い違うことがある
     という教訓。

7. **テストでのSQLAlchemy `DetachedInstanceError`**
   - `test_api_smoke.py`内で、DBセッションを閉じた後に`speaker.id`や
     `utterance.id`にアクセスしたところ、オブジェクトが「detached」状態
     になっていてエラーになった。セッションを閉じる前にIDをローカル変数
     へ退避することで解決。ORMオブジェクトの生存期間(セッションのスコープ)
     を意識する必要があった。

8. **PowerShellでのGitコミットメッセージ記法**
   - Bash向けの`git commit -m "$(cat <<'EOF' ... EOF)"`という複数行メッセージ
     の書き方をそのままPowerShellで実行してしまい、構文エラーになった。
     コミットメッセージを一時ファイルに書き出し、`git commit -F <file>`で
     読み込む方式に変更して回避した。シェルの違い(Bash想定のコマンドは
     PowerShellでは動かない)を意識する必要があった。

9. **GitHubリポジトリ連携の進め方が最初分からなかった**
   - ユーザーはGit自体は使い慣れていたが、「ローカルで作った変更を初めて
     GitHubに上げる」という手順(空リポジトリの作成→リモートURLの登録→
     push)に馴染みがなかった。また作業中にGitHubのページが開けなくなる
     トラブルもあった。`gh`コマンドが未導入だったため、ユーザーに
     GitHub上で空リポジトリを作成してもらい、そのURLを`git remote add`
     する手順を案内する形で対応した。

10. **スクリプトをリポジトリのルートから実行すると`ModuleNotFoundError`**
    - `python scripts/xxx.py`のように素の`python`コマンドで実行すると、
      仮想環境(`.venv`)にインストールした`numpy`等が見つからずエラーに
      なった。`.venv\Scripts\python.exe`を明示的に指定して実行する必要
      があった。

### 工夫した点・対応方法

1. **コードを書くだけで終わらせず、実機(実際のGPU・マイク・Ollama)で
   段階的に検証した**
   - 音声デバイス一覧の取得→内部音声の録音→Whisperでの単体文字起こし
     →Ollama連携→フルE2Eデモ、という順で1機能ずつ実際に動かして確認した。
     これにより、コードレビューだけでは見つからなかった不具合
     (チャンク分割ロジック、モデルタグ名の誤りなど)を早期に発見できた。

2. **AI/ハードウェア依存部分をテストから切り離す設計**
   - 実際のGPUやマイク、Ollamaが無くてもAPI・DBロジックを検証できるよう、
     `FakeOrchestrator`という差し替え可能なテストダブルを用意し、FastAPIの
     依存性注入(DI)の仕組みでテスト時だけ本物のオーケストレーターと
     入れ替えられるようにした。これにより自動テストがCI環境でも軽量に
     動く状態を維持できた。

3. **障害が起きても議事録生成システム全体を止めない、段階的なフォール
   バック設計**
   - 個々のAI処理(文字起こし・話者分離)が失敗しても、そのチャンクだけ
     スキップしてパイプライン全体は継続する設計にした。さらにメインループ
     自体が致命的エラーで落ちた場合でも、会議のステータスを確実に
     `finalize`する保護コードを入れ、データが不整合な状態で残らないように
     した。

4. **手動編集を上書きしない、というデータ整合性の設計**
   - 議事録生成のたびにDBから最新のスナップショットを読み直し、そこに
     差分を当てる方式にすることで、ユーザーがUI上で手動編集した内容が
     AIの次回生成で勝手に消えてしまわないようにした。

5. **TTS(`pyttsx3`)で合成した固定デモ音声を使い、E2Eテストを再現可能に
   した**
   - 実際の会議を録音しなくても、毎回同じ内容の音声を生成して通しの動作
     確認ができるように`generate_demo_audio.py`と`run_demo_e2e.py`を用意
     した。これにより「毎回同じ入力で結果を比較できる」再現性のある
     検証環境を作れた。

6. **文字コード破壊など「原因が分からない異常」に遭遇した際は、まず
   影響範囲を確認してから最小限の修正に留める**
   - `chunker.py`が壊れた際、他のファイルへの影響有無をまず確認し、
     被害が1ファイルに留まっていることを確かめた上で、そのファイルだけ
     クリーンな内容で書き直す(かつPythonでバイト列を検証する)という
     地に足の着いた対応を取った。

### 今後の課題(このセッション終了時点での引き継ぎ事項)

- `HF_TOKEN`が未設定のため、話者分離(pyannote)は実機で未検証のまま
  セッションを終えた(→この課題は「セッション2」で解消された)。
- 話者クラスタリングの精度そのものは未検証。

## セッション2: HF_TOKENの手動セットアップと話者分離の動作確認(2026-08-10)

### 背景

前回までの開発(「セッション1」)で「`HF_TOKEN`(Hugging Faceのアクセス
トークン)が未設定のため、話者分離(pyannote)は検証できていない」という
状態で引き継いだ。今回はこの手動セットアップを行い、実際に話者分離まで
含めて動作確認することが目的だった。

### つまずいた点・苦戦した点

1. **Hugging Faceの「利用規約同意」の仕組みが分かりにくかった**
   - pyannoteの学習済みモデルは「gated(門番付き)モデル」と呼ばれ、モデルの
     ダウンロード前にWebページ上で利用規約に同意する必要がある。しかも
     関連する複数のモデル(`speaker-diarization-3.1`, `segmentation-3.0`,
     `embedding`)それぞれで個別に同意が必要だった。
   - 同意フォームの「Company/university」「Website」といった入力欄の意味が
     分かりにくかった(個人利用でも適当な値で通ることを確認した)。

2. **`.env`と`.env.example`の違い、保存・反映のタイミングが分かりにくかった**
   - どちらのファイルを編集すべきか混乱しやすい。
   - ファイルを保存しても、サーバーを再起動しないと環境変数が反映されない。

3. **表面的なエラーメッセージだけでは原因が分からない、根深い依存関係の
   バージョン不整合が複数重なっていた**(ここが最も苦戦した部分)
   - `Pipeline.from_pretrained() got an unexpected keyword argument 'token'`
     → コードが渡す引数名(`token`)と、インストール済み`pyannote.audio==3.3.2`
     が期待する引数名(`use_auth_token`)が異なっていた。
   - 引数名を直しても `hf_hub_download() got an unexpected keyword argument
     'use_auth_token'` → 今度は`huggingface_hub`側が1.0以降で`use_auth_token`
     を完全に廃止しており、古い`pyannote.audio`と噛み合わなくなっていた。
   - さらに `SpeakerDiarization.__init__() got an unexpected keyword argument
     'plda'` → そもそも使っていたモデル`pyannote/speaker-diarization-
     community-1`自体が、最新の`pyannote.audio 4.0`系専用に作られたもので、
     プロジェクトが(VRAM急増バグ回避のため意図的に)固定している`3.3.2`系
     とは根本的に非互換だった。
   - 1つのエラーを直すと次のエラーが出る、という「エラーの層」を1枚ずつ
     剥がしていく必要があり、原因特定に一番時間がかかった。

4. **Windows特有のライブラリの不具合**
   - `speechbrain`(pyannoteの話者embeddingモデルが内部で使うライブラリ)に、
     Windowsのパス区切り(`\`)を想定していない判定処理があり、不要な`k2`
     モジュールを要求して`ImportError`で落ちる、という一見関係ない場所で
     クラッシュする不具合があった。
   - これは`speechbrain`本体の既知バグ(修正PRはあるが未リリース)で、
     こちらのコードの問題ではなかった分、原因特定に時間がかかった。

5. **Pythonの例外にならない、プロセスそのもののクラッシュ**
   - Whisper(ctranslate2)と話者分離(torch)を両方GPUで動かした際、
     `Could not load symbol cudnnGetLibConfig. Error code 127` という
     メッセージの直後にプロセスが無言で終了する現象が発生。
   - 通常のPythonの`try/except`では捕まえられない、ネイティブライブラリ
     (cuDNN)のバージョン競合が原因で、ログのtracebackが出ないため
     「何が起きたか」を推測するのに苦労した。

6. **LLM(Qwen3)の出力ゆらぎによる想定外のバグ**
   - 議事録生成AIが、本来「辞書のリスト」で返すべき項目
     (`changes_from_previous`)を「文字列のリスト」で返してしまい、
     画面表示時に500エラーになった。検証処理が「リストかどうか」しか
     チェックしておらず、「リストの中身の型」まで見ていなかったのが原因。

7. **コミット直前にAPIトークンの誤混入を発見**
   - `.env`(本物のトークンが入る、Git管理対象外のファイル)を編集する過程で、
     誤って`.env.example`(Gitで管理される、サンプル用のファイル)側にも
     実際のトークンの値が書き込まれてしまっていた。
   - `git diff`でコミット前に差分を必ず確認する習慣のおかげで、公開前に
     気づいて修正できた。

### 工夫した点・対応方法

1. **エラーを1つずつ、実際にコマンドで再現・検証してから直す**
   - チャットのログを読むだけで判断せず、実際にPythonスクリプトで
     「そのステップだけ」を単独実行して、エラーが再現するか・修正で
     直るかをその都度確認しながら進めた(推測で直して終わり、にしない)。

2. **VRAM対策のために元々あった「3.3.2固定」という制約を守ったまま、
   モデル選定を修正**
   - 最新モデル(`community-1`)を使うのをやめて、`3.3.2`と互換性のある
     一世代前のモデル(`speaker-diarization-3.1`)に切り替えることで、
     既存のVRAM対策の方針を崩さずに問題を解決した。

3. **サードパーティライブラリの既知バグを、ライブラリ自体を書き換えずに
   実行時パッチ(モンキーパッチ)で回避**
   - `speechbrain`の不具合は、Windows専用の直接的な原因(Unix限定のパス
     判定)が特定できたため、起動時に該当処理だけを差し替えるコードを
     自作して対応した。将来ライブラリ側が修正されても実害がない書き方
     (例外時は元の挙動にフォールバック)にしている。

4. **GPU競合は「両方GPU」を諦め、負荷の低い方をCPUに逃がす設計に変更**
   - cuDNNのバージョン競合はライブラリ間の根本的な問題で、その場では
     修正できない。文字起こし(Whisper)をGPUに残し、話者分離をCPUに
     回すことで、機能を落とさずに安定性を確保した(README にも
     理由を明記し、あとで見返せるようにした)。

5. **LLM出力の型チェックを「型」だけでなく「中身の型」まで厳格化**
   - 既存の「前回議事録を上書きしない」という設計方針(README記載)に
     合わせて、不正な形式が来た場合は素直に「失敗」として前回の議事録を
     保持する、という一貫した挙動になるように検証処理を強化した。

6. **コミット前に必ず`git status` / `git diff`で内容を目視確認する**
   - 今回、実際にAPIトークンの誤混入を防げたのはこの手順のおかげ。
     「変更した意図」と「実際の差分」が一致しているかを毎回確認する
     ことの重要性を再認識した。

### 今後の課題(未解決)

- **話者クラスタリングの精度**: 実際に試した際、短い会話(1分程度)で
  `speaker_01`〜`speaker_10`以上に分裂してしまう問題が残っている。
  `SPEAKER_SIMILARITY_THRESHOLD`(現在0.45)の調整、または
  `pyannote/embedding`(比較的古いモデル)自体の精度限界の可能性がある。
  次回以降のセッションで取り組む予定。
  → この課題は「セッション3」で対応した。

## セッション3: 話者クラスタリング精度の改善(2026-08-24)

### 背景

セッション2の未解決課題だった「短い会話で話者が `speaker_01`〜`speaker_10` 以上に
分裂する」問題に取り組んだ。しきい値だけの問題ではなく、割り当て方そのものに
過分裂を招く実装があった。

### つまずいた点・苦戦した点

1. **症状は「しきい値が厳しい」に見えたが、原因は複数重なっていた**
   - 既定のコサイン距離しきい値 `0.45` は、pyannote 3.1 本体のクラスタしきい値
     (約 `0.70`) よりかなり厳しく、同一人物でも新規IDになりやすかった。
   - それ以上に効いていたのが、(a) 0.3秒程度の短い区間ごとに古い
     `pyannote/embedding` でベクトルを取り直していたこと、(b) Whisperの
     セグメントごとに `assign()` を呼んでいたこと。同じチャンクの同じ話者でも
     短いクリップのノイズで別IDになっていた。

2. **話者分離パイプラインは、すでに良い embedding を持っていた**
   - `speaker-diarization-3.1` は内部で WeSpeaker
     (`pyannote/wespeaker-voxceleb-resnet34-LM`) を使っている。
   - それなのに横断クラスタリングだけ古い `pyannote/embedding` を別ロードしており、
     モデルの世代も尺度も揃っていなかった。
   - パイプラインは `return_embeddings=True` で「ローカル話者ごとの代表ベクトル」
     を返せる。短いクリップを切って再計算する必要はなかった。

### 工夫した点・対応方法

1. **短いクリップごとではなく、チャンク内のローカル話者ごとに1つの embedding を使う**
   - `return_embeddings=True` の代表ベクトルを、そのローカルラベルの全区間で共有する。
2. **チャンク内の同じローカルラベルは `assign()` を1回だけにする**
   - Whisperセグメントの数だけクラスタリングしていたのをやめ、過分裂を止めた。
3. **L2正規化してから距離計算・重心更新する**
   - ベクトルの長さの違いで距離が歪まないようにした。話者統合時も正規化する。
4. **既定しきい値を `0.45` から `0.65` へ変更**
   - オンライン(貪欲)割当なので、バッチクラスタの `0.70` より少し厳しめに残した。
   - `.env` の `SPEAKER_SIMILARITY_THRESHOLD` で調整できる。
5. **診断用スクリプト `scripts/inspect_speaker_clustering.py` を追加**
   - 実音声でチャンクごとのローカル/グローバル話者数と距離を見られるようにした。

### 今後の課題

- 実会議音声での最終確認は、このセッションでは自動テスト(ロジック)まで。
  実マイク/Zoomでの過分裂が残る場合は、診断スクリプトの距離分布を見て
  しきい値を微調整する。
- 声がとても似ている別人をまとめすぎる場合は、しきい値を少し下げる
  (例: `0.55`)。
  → 実機で「全員 `speaker_01`」になるまとめすぎは「セッション4」で対応した。

## セッション4: デスクトップ起動と話者のまとめすぎ対策(2026-08-24)

### 背景

セッション3のあと、実際にデスクトップから使ってみる段階に入った。
「PowerShellでサーバーを起ち上げる」運用は普段使わない人には重いので、
ダブルクリックで起ち上がるようにしたうえで、初回の実機確認で2つの障害に当たった。
1つ目は起動直後のプロセスクラッシュ、2つ目は話者が全員 `speaker_01` にまとまる問題。
セッション3は過分裂(同じ人が何人もに分かれる)の修正だったが、実機では逆の
まとめすぎが出た。

### つまずいた点・苦戦した点

1. **使う側から見ると「サーバーを起ち上げる」が何なのか分かりにくい**
   - 開発者には `uvicorn` が当たり前でも、利用者には「黒い画面にコマンドを打つ」
     こと自体が障壁になる。Cursorは開発用で、本番利用には不要、という説明も
     最初は伝わりにくかった。
   - 「デスクトップにアイコンがあって、クリックしたら使える」形が欲しい、
     という要望は機能追加というより、届ける方法の問題だった。

2. **起動はできたのに、会議開始直後にプロセスごと落ちた**
   - ログは `Could not load symbol cudnnGetLibConfig. Error code 127` の直後に
     終了コード `3221226505` で止まり、Pythonのtracebackが出ない。
   - セッション2で既知の「Whisper(cuda)とpyannote(cuda)のcuDNN競合」そのもの。
   - `.env` には `DIARIZATION_DEVICE=cpu` と書いてあるのに、実行ログは
     `device=cuda` になっていた。設定ファイルを「読んだつもり」と
     「実際に効いている」が一致していなかった。

3. **`.env` の改行が壊れ、設定行がコメント扱いになっていた**
   - `DIARIZATION_DEVICE=cpu` が、直前の日本語コメントと同じ行に連結されていた。
     行頭が `#` のため pydantic-settings はコメントとして無視し、
     `config.py` の当時の既定値 `cuda` に落ちていた。
   - `MINUTES_UPDATE_CHAR_THRESHOLD` も同様にコメント行へ飲み込まれていた。
   - 画面上は「cpuと書いてある」ので、原因にたどり着くまで時間がかかるタイプの
     不具合。コメントの文字化けと合わさって、目視でも気づきにくかった。

4. **セッション3の修正が、別の失敗モードを目立たせた**
   - 過分裂対策として「チャンク内の同じローカルラベルは1回だけ割当」にしたため、
     pyannoteが8秒チャンクを1人にまとめると、そのチャンクの発言がすべて
     `speaker_01` になる。
   - 実機ではYouTube動画をPCスピーカー経由で取り込み、冒頭8秒で3人が自己紹介
     していた。文字起こしは「ケビンです」「ブカケです」「ギャンマンです」と
     分かれているのに、話者IDだけが同じ、という分かりやすい失敗になった。
   - しきい値をいじるだけでは足りない。pyannoteが返すラベルが1種類なら、
     オンラインクラスタリングは1回しか呼ばれない。

5. **PC内部音声(ループバック)の制約が、モデルの限界と重なる**
   - 全員の声が同じスピーカーから出て、1本のモノラル音声になる。
     Zoomのようにマイクが分かれている会議より、話者分離は本質的に難しい。
   - 8秒チャンクは準リアルタイムのため必要だが、自己紹介が連続する冒頭とは相性が悪い。

### 工夫した点・対応方法

1. **ダブルクリック用ランチャーを追加した**
   - `scripts/start-app.bat` と `scripts/start_app.py` で、仮想環境の確認、
     Ollamaの生死確認、サーバー起動、ブラウザ起動までを一連で行う。
   - 初回起動時にデスクトップへ「議事録アプリ」ショートカットを作る。
   - すでに `localhost:8000` が開いていれば二重起動せず、ブラウザだけ開く。
   - 黒い画面は「動いている印」兼「閉じると停止」の操作系として残した。
     完全に隠すと止め方が分からなくなるため。

2. **`.env` をサンプルから作り直し、設定の安全網をコード側にも置いた**
   - 壊れたコメント行を手で直すのではなく、`.env.example` を正として
     トークンだけ引き継いで書き直した。
   - `diarization_device` のコード既定値を `cuda` から `cpu` に変更し、
     `.env` が読めなくてもクラッシュ側に倒れないようにした。
   - Windowsで Whisper と pyannote が両方 `cuda` なら、起動時に話者分離だけ
     `cpu` へ強制する validator を追加した。設定ミスでプロセスが死ぬより、
     遅くても動くほうを選ぶ。
   - `.env` の読み込みエンコーディングを `utf-8-sig` にし、BOM付きでも
     先頭キーが壊れないようにした。

3. **「pyannoteが1人にまとめた」ケースを、文字起こしの区切りで再分割する**
   - ローカル話者が2人以上なら、従来どおり区間の重なりで割り当てる。
   - 1人(または失敗)のときは、Whisperの発言区間ごとに embedding を取り、
     `SpeakerRegistry` で再クラスタリングする。
   - 同じローカルラベルでも embedding が大きく違う区間は独立に割り当てる。
   - これにより「ラベルは1つ、発言テキストは3人」のときに、話者IDを
     分け直せるようにした。

4. **分かっている人数を、開始画面からヒントとして渡せるようにした**
   - 「話者数(任意)」入力を追加し、`min_speakers` として pyannote に渡す。
   - 参加者一覧の人数や `.env` の `DIARIZATION_MIN_SPEAKERS` も同じヒントに使う。
   - 1人会議を無理に分割しないよう、2以上のときだけ有効。
   - 自己紹介が連続する検証動画では、開始前に `3` を入れるのが一番効く。

5. **ロジックはモデルを回さずに自動テストした**
   - まとめすぎの再分割、ヒント人数の解釈、Windowsのcuda二重指定の回避は
     pytestで固定した。実音声の最終確認はランチャー再起動後の目視に残している。

### 今後の課題(未解決)

- PCスピーカー経由の動画音声は、人数ヒントを出しても別人の embedding が
  近く、まだ1人に寄ることがある。本番想定のZoom(マイクが分かれる)での
  確認がまだ残っている。
- 話者数を開始前に入力する運用は、人数が分からない会議では使えない。
  会議の途中から人数が分かる場合の追従は、参加者追加に頼っている。
- ランチャーは黒い画面を残している。トレイ常駐や終了ボタン付きの
  小さな窓にすると、さらに気軽になる余地がある。

## セッション5: 話者の過剰検出・準リアルタイム表示・会議中の操作負荷(2026-08-27)

### 背景

実動画(5〜6分、実際の発話は4名程度)で検証したところ、話者数が8人まで増え、
先頭の発言が `speaker_02` になり、発言していない番号が文字起こしに出ない、
という不整合が出た。あわせて「議事録を主に見たい」「文字起こしが動画終了後に
まとめて出る」「会議中の話者割当が忙しすぎる」という使い勝手の問題が残っていた。

### つまずいた点・苦戦した点

1. **「話者数」を pyannote の `min_speakers` として毎チャンク渡していた**
   - セッション4では「分かっている人数を下限ヒントにする」と過まとめ対策に
     した。しかし約8秒の窓に「最低N人いる」と強制すると、実際は1〜2人しか
     話していなくても分割される。上限(`max_speakers`)は未使用だった。
   - 利用者は「会議全体の人数」のつもりで入力するのに、実装は「この瞬間の
     最低人数」だった。意味がずれると、対策が逆に過剰検出を生む。

2. **話者行と文字起こしが別経路で作られていた**
   - pyannote の全区間に `Speaker` 行を作り、Whisper と時間重なりがある
     区間だけが発言になる。ノイズや VAD 落ちの区間は「話者パネルにはいるが
     文字起こしには出ない」幽霊話者になる。
   - 先頭が `speaker_02` なのは、時系列最初のローカル話者が発言に乗らず、
     2番目だけが文字起こしと重なったため。

3. **「リアルタイムに見えない」主因が処理速度だけではなかった**
   - WebSocket は `text` を送り、画面は `raw_text` だけを読んでいた。
     会議中の本文は空で、終了後の REST 再取得で初めて文章が出る。
   - これに加え、Whisper → pyannote(CPU) → 議事録LLM が同一スレッド直列
     だった。pyannote が8秒を超えるとキューが伸び、映像終了後に追いつく。

4. **会議中の話者操作が、画面の定期再描画とぶつかった**
   - 発言のたびに 1.5 秒後へ `Speakers.refresh()` し、`innerHTML = ""` で
     話者パネルを作り直していた。入力中の名前も統合先の選択も消える。
   - 名前欄に Enter ハンドラが無く、「割当」を押しても再描画で値が空に
     なっているように見えた。
   - 統合 API は `merged_into_id` を書くが、ライブ画面は元の `speaker_id`
     のまま表示していた。終了後の REST では直ることがあり、「反映がまちまち」
     に見えた。

5. **会議に集中できない操作量**
   - 話者が増えるたびに手入力と統合が必要で、議事録を見るどころではなくなる。
   - ツールは内容を長く保存しない前提なので、終了後に全文を残す手段も必要。
     画面を全部選択してコピーするのは実務的に厳しい。

### 工夫した点・対応方法

1. **人数入力の意味を「会議全体の上限」に直した**
   - 8秒チャンクへ会議全体の N を `min_speakers` として渡さない。
   - pyannote へは `max_speakers=N` のみ。未指定なら自動推定のまま。
   - `SpeakerRegistry` も上限に達したら閾値超えでも最近傍へ割当し、新規 ID を
     増やさない。
   - まとめすぎ対策(ローカル1人なら Whisper 区間で再分割)は残した。

2. **幽霊話者を作らない**
   - Whisper と時間重なりがある pyannote 区間だけ `registry.assign` する。
   - 話者パネルは未マージかつ、実際に発言がある人だけ出す。

3. **本文を先に出し、話者分離と議事録は横で進める**
   - WS に `raw_text` / `effective_text` を載せ、画面もそれを読む。
   - Whisper 完了時点で発言を保存・配信し、話者は後から付ける。
   - pyannote と Qwen3 を別スレッドにし、文字起こしを止めない。
   - Windows では Whisper=GPU・pyannote=CPU のまま重ねる(両方 CUDA は
     cuDNN 競合で落ちるため)。
   - `beam_size` を 5→2、議事録更新を 300文字 / 60秒にして、会議中に
     議事録が見える間隔へ寄せた。

4. **見た目で話者と議事録を追いやすくした**
   - 話者ごとに固定色(文字起こしの左線と名前、話者パネル)。
   - 左を議事録(主面)、右に文字起こし・話者・参加者。

5. **会議中の入力を再描画で消さない**
   - 話者パネルを作り直す直前に、入力中の名前・プルダウン・カーソル位置を
     保存して戻す。フォーカスも奪わない。
   - 統合先は `merged_into_id` をたどり、表示名と色を統合先に合わせる。
     `speaker_06` を拠点長へ統合したら、既存行もすぐ拠点長になる。
   - 名前欄の Enter で割当できるようにした。

6. **手入力だけでなく、先に登録した名前から選べるようにした**
   - 参加者一覧へ名前を入れておくと、話者行の「一覧から選択」プルダウンから
     割り当てられる。選んだ時点で割当する。
   - 一覧に無い名前は従来どおり手入力もできる。

7. **終了後に残せるよう、コピーボタンを付けた**
   - 議事録と文字起こしそれぞれに「コピー」を置き、整形したプレーンテキストを
     クリップボードへ入れる。全部選択しなくてよい。
   - 内容が無いときは押せない。コピー後は「コピーしました」と出す。

8. **モデルを回さずに自動テストした**
   - 重ならない turn は Speaker を増やさないこと、上限で新規発行しないこと、
     WS ペイロードに `raw_text` があることを pytest で固定した。

### 今後の課題(未解決)

- 話者数を開始時に入れないと上限が効かない。人数不明の会議では、同一人物の
  分裂はまだ起こり得る。
- PCスピーカー経由の動画は embedding が近く、上限を入れても誤結合・誤分裂の
  両方があり得る。Zoom(マイクが分かれる)での確認はまだ残っている。
- 単語単位のストリーミング文字起こしにはしていない。追いついているときの
  遅延はチャンク長(約8秒)+数秒が下限。
- 会議前(開始ボタンより前)に参加者名を入れておく機能は無い。会議開始後に
  参加者一覧へ追加する運用になる。
  → この課題は「セッション6」で対応した。

## セッション6: 会議開始前の参加者登録と話者プルダウン(2026-08-27)

### 背景

セッション5で、話者パネルに「一覧から選択」プルダウンを付け、参加者一覧の
名前から割り当てられるようにした。ただし参加者は会議IDに紐づくため、会議は
「会議を開始」で初めて作られる。開始前に名前を入れても
`participants.js` の `_add()` が `meetingId` 無しで return し、開始時の
`Participants.reset()` が画面上の入力も捨てていた。実運用では開始前から
「三谷」「拠点長」など参加者が分かっているので、開始前に登録して開始後の
プルダウンから選べるようにした。

### つまずいた点・苦戦した点

1. **参加者と会議の作成順が逆だった**
   - 欲しい操作は「先に名前、あとから会議開始」。データモデルは「先に会議、
     その会議へ参加者」。会議なしで参加者APIを呼ぶと404になる。
   - バックエンドを「会議なし登録」に広げる案もあるが、会議に紐づかない
     名簿の寿命や、終了後の次会議への持ち越し規則が増える。フロントの
     一時リストに閉じる方が変更範囲が小さい。

2. **`reset()` が開始前の入力を消していた**
   - `startMeeting()` は会議作成直後に文字起こし・議事録・話者と一緒に
     参加者も `reset()` していた。会議を作り直せたとしても、開始前に
     画面へ出した名前は残らない。
   - 開始失敗時に pending を残す必要もある。会議作成の前に消すと、
     失敗しても名前が消える。作成成功後に API へ流し、失敗したら
     まだ pending に残す、という順番が必要だった。

3. **終了後も `meetingId` が残る**
   - 終了後も文字起こしや話者割当で会議IDを使うため、`meetingId` を
     null にはできない。開始前判定を `!meetingId` だけにすると、2回目の
     会議の開始前追加が旧会議の API へ行ってしまう。
   - `isRunning` を別途持ち、会議中だけ API、それ以外は pending にした。

4. **話者上限ヒントとの関係**
   - `resolve_max_speakers` は参加者人数もヒントにする。開始時に4人
     登録すると上限4になるのは意図どおり。開始前の pending は DB に
     無いので人数に入らないが、開始成功直後にまとめて API 登録する。
     音声チャンクは約8秒なので、通常は最初の話者分離より先に登録が終わる。

### 工夫した点・対応方法

1. **会議を先に作らず、開始前はフロントの一時リストに置いた**
   - `_pending` に名前を積み、一覧表示と削除もこの配列だけで動かす。
   - 空文字・重複は追加しない。会議が無いのに API を叩かないので 404 にならない。
   - 「会議なしでも参加者を登録できる API」は作らなかった。名簿の寿命や
     次会議への持ち越し規則がサーバー側に増えるのを避け、変更を UI に閉じた。

2. **開始の成功・失敗で、消す／残すを分けた**
   - 開始時に `Participants.reset()` しない。作った直後に捨てると、開始前の
     入力が消える。
   - 会議作成と `meetingId` 設定のあと、pending を1件ずつ `Api.addParticipant`。
     全部終わってから `Participants.refresh()` → `Speakers.refresh()` し、
     話者プルダウンの「一覧から選択」に名前が乗る。
   - 途中まで成功した名前だけ pending から外し、失敗した残りは画面に残す。
     会議作成自体が失敗したときは、開始前の名前を一切消さない。

3. **「会議IDがある」と「会議が進行中」を分けた**
   - 終了後も文字起こし・話者割当で `meetingId` が必要。ID の有無だけで
     判定すると、次の会議の開始前追加が旧会議の API に行ってしまう。
   - `isRunning` を持ち、会議中だけ API、それ以外は pending。
     2回目以降も「開始前に名前を足す」と同じ操作になる。

4. **次の会議へ名簿をコピーしない**
   - 終了成功時に pending を空にする。開始時に API へ流すのは pending だけ。
     前の会議の参加者行は新しい会議には複製しない。
   - 終了直後の話者パネル再描画では、直前の名簿と `display_label` を
     プルダウンに残す。会議中の入力保持・`merged_into_id` 解決・コピー
     ボタンには手を入れていない。

5. **話者上限ヒントは、開始後に登録された人数で効くようにした**
   - pending のあいだは DB に無いので `participant_count` に入らない。
   - 開始成功直後にまとめて API 登録する。チャンクは約8秒なので、通常は
     最初の話者分離より先に人数が乗る。4人登録すれば上限4、という既存の
     意味は維持した。

6. **画面上の案内を、開始前から使えることが分かる文に直した**
   - 「会議開始前から名前を追加できます。開始後は話者パネルの
     『一覧から選択』から割り当てられます。」
   - バックエンド契約は変えず、pytest(33件)も既存のまま通した。

### 今後の課題

- 開始前の pending はページをリロードすると消える。サーバー側の下書きは無い。
- 開始直後のごく短い間に最初のチャンクが処理されると、その瞬間だけ
  参加者人数が上限ヒントに乗らない可能性がある(通常は8秒チャンクより
  登録のほうが早い)。
